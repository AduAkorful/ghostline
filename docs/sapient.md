# Sapient integration spike

**Checked:** 2026-10-22 against Tari's [integration reference](https://universe.tari.mw/integration/llms-full.txt) and the deployed demo UI. The browser simulation stays local by default. `play.html` loads Tari's connector script with `defer` when the page opens; the simulation does not call the wallet unless the user starts live mode.

## Verified wallet surface

- `window.tari.request({ method: "tari_getNetwork" })` reads the network without connecting. Network values must be compared case-insensitively with `esmeralda`.
- `tari_requestAccounts` prompts for an account; `tari_getCapabilities` must be used for feature detection; `tari_getBalances` returns native units with a resource divisibility field.
- `tari_createTransactionRequest` with `kind: "sendPrivately"` takes `resourceAddress`, `recipientWalletAddress`, and `amount`, plus optional fee/memo/proof fields. It has no arbitrary spend-condition or script-path argument. It cannot directly create Ghostline's script-locked channel output.
- `withdrawStealthAndExecute` exposes the selected amount as a `Bucket` and runs caller-supplied follow-up instructions. A prototype can pass that bucket to a custom template method and turn it into Ghostline's script-locked output, but it does **not** preserve deposit privacy: the stealth transfer statement must set its public `revealed_amount` to the amount being withdrawn. For a channel open, that reveals the exact deposit. This route is therefore rejected for Ghostline's privacy-preserving flow, even though the template call itself is technically possible.
- `Bucket::stealth_transfer` in the installed template library only supplies the input bucket when `revealed_amount` is nonzero, and the value is included in the transfer statement. A passing template test would not change that public disclosure. Do not describe this as a masked-deposit open or expose it as a live demo path.
- The documented `scriptPathSpend` capability is limited to supported HTLC claim/refund flows; the current integration reference does not document arbitrary script-path spending for Ghostline's custom payer-expiry refund condition. Even a privacy-preserving open would need a supported way for the payer to reclaim the channel output after expiry.
- Tari deliberately exposes no arbitrary-message signing method. The wallet ownership challenge is signed under Tari's fixed domain and cannot authorize Ghostline vouchers. Voucher signatures therefore use an ephemeral browser key in the signed Ghostline channel parameters. Keep that private key in the browser (`localStorage` with a pending funding transfer so another tab can retry, and `sessionStorage` while a live channel is open); it must never be sent to the API.
- User rejection is code `4001`; not-connected is `4100`; unsupported method is `4200`; network rejection is `-32603`. Treat these separately and keep the simulated demo available.

## Relay-path assessment

The contest plan's relay path C is technically distinct from the unsupported direct-open path: Sapient can privately transfer a bounded Esmeralda test amount to a service wallet, and the relay can use its wallet daemon to create the script-locked channel. This makes the relay a custodian of the test deposit and gives its operator the ability to observe the funding transfer and channel state. It is not equivalent to the user's wallet opening its own Ghostline channel.

The SDK and CLI support a separate expiry-refund key (`--refund-hex` on channel setup). The browser retains the voucher-signing key, while a relay key appears only on the `AfterEpoch` refund branch. The existing settlement template verifies vouchers against the browser's payer public key, so possession of the refund key alone cannot create an early settlement voucher. SDK and contract-engine regression tests confirm the separation. The relay creates channels, registers per-channel quote, authorization, and payout keys, and issues authenticated encrypted recovery receipts after opening and each accepted call. The browser retains the receipt in tab session storage and can present it to `/demo/recover` or with the next signed paid call to restore ledger and signer files after process state is lost. The receipt is a bearer recovery credential, encrypted with `GHOSTLINE_DEMO_STATE_KEY`; it is sent only to the configured relay over HTTPS. The payer signing secret, seed phrase and Sapient credentials stay out of relay requests.

The paid API has an opt-in relay API for `/demo/session`, `/demo/open`, `/demo/refund-funding`, `/demo/settle`, `/demo/refund`, `/demo/status`, and `/demo/tx-status`, plus a `ghostline-paid-api relay` startup mode for a dynamic channel directory. Its open path confirms Sapient funding from the indexer’s `GET /transactions/{id}` record (`summary.outcome`) and, if needed, `GET /transaction-receipts/{id}`. Public Esmeralda 0.47 nodes 404 `GET /transactions/{id}/result` even when that body and receipt exist, so the relay does not treat a `/result` 404 as a dropped deposit or treat `stealth_utxos.list` as finality. Before broadcasting, it requires that list to show each verified funding commitment as an unspent key-path output. Other unspent outputs do not block that open. The open locks only those funding outputs through `accounts.create_stealth_transfer_statement` (`InputSelection::Specific`) and pays the fee from the fee account with `transactions.submit` and that statement's `lock_id`. A local open without a funding commitment still uses `accounts.stealth_transfer`, which cannot name an output and merges the fee into the transfer. The configured open max fee is a ceiling. The submitted cap is the dry-run `required_fee`. This pinned open is unit-tested and has not been broadcast on Esmeralda. The statement call holds the funding output for five minutes. One funding transaction keeps one channel file. A submitted open is resumed from that file, and a rejection does not create another output. The service ledger file is created before the live transfer. It then unblinds relay-owned private XTR outputs on that transaction body and requires their aggregate to equal the configured deposit. New funding transfers encrypt a `G2:<session-id><payer-hex>:<refund-address>` memo to the relay; older transfers used `Ghostline:<session-id>` only. The relay matches that memo to the requesting session and, after a host restart that dropped the in-memory session, can rebuild payer and refund details from a v2 memo. It does not expire an already-funded session after ten minutes. Sapient submits this memo encrypted to the recipient, so it binds a public transaction to the refund address chosen before funding without putting that session link in public transaction fields. The relay cannot use its walletd `transactions.wait_result` or `transactions.get` for the funding transfer because Sapient submits it from the user's wallet. The browser keeps its voucher-signing key local (including with the saved pending transfer), retries the same funding transaction without asking for a second transfer, submits real signed vouchers, and exposes an expiry-refund action. If an approved Sapient transfer finalized but channel opening failed, the browser can request a private return transfer to the refund address bound to that session, or abandon the saved transfer locally to unlock live mode in this browser; abandoning does not recover funds. The relay verifies the same encrypted memo before returning funds and accepts no caller-supplied refund address. The session ID is a bearer capability, stored with the pending transfer in browser local storage so another tab can offer recovery; keep access to the browser profile private. The live page surfaces an unlock reminder if Sapient stays pending. The relay records refund intent before sending funds and fails closed after an interrupted send rather than risking a duplicate payment. Settlement finality is checked through the indexer. The 2026-10-22 QA report reached the Render v0.4.0 Esmeralda health endpoint, but the full Sapient lifecycle has not yet been verified against the current implementation.

The live page tells users to switch Sapient to Esmeralda, obtain test XTR from Sapient's built-in faucet, and wait for finality before connecting. It checks `tari_getBalances` when the wallet exposes a balance and stops before requesting a transfer when the reported balance is below the 51 µT deposit. Some wallet profiles do not grant balance viewing; in that case, Sapient remains the final balance check during approval and the page explains the minimum deposit plus additional wallet fees. Sapient's displayed balance may be stale immediately after a faucet transfer; refresh its wallet/account view, wait for finality, then reload the demo before retrying. The browser now reports which live-setup stage failed and includes the returned error so a wallet or relay failure is diagnosable without opening DevTools.

The default live demo amount is 51 µT: five 10 µT calls can settle 50 µT, leaving only the template's required 1 µT fixed-shape change output. That final micro-unit remains encrypted to the ephemeral payer key and is not returned to Sapient after settlement. An unsettled channel can still take the expiry branch and return the full 51 µT privately. Do not increase `GHOSTLINE_DEMO_DEPOSIT` without implementing and verifying payer-change recovery.

Render packaging is in `deploy/` with a pinned Docker build, loopback-only walletd startup, deterministic opener/fee accounts, Blueprint, and operator instructions. Startup emits the public fee-account address. `account-ensure` does not publish that component; when the indexer has never created it, startup claims the Esmeralda faucet once and pays the fee from the new account. That claim is public. A transfer to the printed address does not create the component. Render has been deployed and Sapient funding transactions finalized, but the funded QA runs have not yet completed channel opening, paid calls, settlement, and refund. The wallet seed, database password, and opener account's matching view-only claim key are deployment secrets; the claim key is separate from the seed phrase and voucher-signing key. The Blueprint uses opener index 2, so its claim secret must be the view key at index 2, not index 0. Before returning a funding address/session, the relay compares the configured secret's public key with walletd's view-key record for that opener index. A mismatch stops setup before any wallet approval.

The relay now writes its session map, channel-to-key/path map, per-channel quote keys, funding idempotency records, prepared open attempts, pending funding-refund intents, and submitted settle/refund transaction IDs atomically to `GHOSTLINE_LEDGER_PATH/relay-state.json` with owner-only permissions. Startup restores those records and per-channel payment terms from the same state directory; process-restart unit tests cover saved session, channel, funding retry, and funding-refund state. The channel ledgers and channel files remain in `GHOSTLINE_LEDGER_PATH/channels`.

Recovery receipts remove the relay-ledger dependency on Render's ephemeral filesystem, but channel signing still depends on walletd being able to recreate its seed-derived key references after replacement. That behavior has not been verified on a deployed Render instance. An uptime monitor reduces free-tier idle sleeps; it cannot prevent deploys, crashes, or host restarts. Do not describe the hosted path as restart-proof until walletd recovery is tested with the actual deployment. Do not deploy real-money credentials or expose a wallet daemon outside loopback.

## Required live-mode checklist

- [ ] For a direct, non-custodial open, wait for Sapient support for custom-condition stealth output creation that keeps the input amount hidden; do not use `withdrawStealthAndExecute` with a nonzero `revealed_amount` for Ghostline deposits.
- [ ] For the custodial relay alternative, prove private Sapient funding → walletd channel open → paid calls → settlement → expiry refund returned privately to the funder.
- [ ] Demonstrate recovery after an unexpected Render restart, including the channel mask, latest accepted voucher, and any refund still due.
- [ ] Persist the channel mask and wallet signer references in a protected location, with explicit restart recovery; Render's free ephemeral filesystem alone is insufficient.
- [ ] Demonstrate voucher acceptance, service settlement, finalized transaction lookup, and payer remainder recovery after expiry.
- [ ] Verify per-channel service authorization and payout keys are fresh and not reused.
- [ ] Exercise connector absent, wrong network, low balance, rejected popup, unsupported method, chain rejection, cold backend, and pending transaction fallbacks.
- [ ] Record exact tested Sapient version and new transaction identifiers in `demo/ui/evidence.json`.

## Transaction request guidance

The live flow uses the persistent request trio so page reloads can resume a wallet approval:

1. `tari_createTransactionRequest` from an explicit user action.
2. Poll `tari_getTransactionRequest({ requestId })` until its status is not `pending`.
3. Call `tari_submitTransactionRequest({ requestId })` only after approval.

Do not probe a public Tari node adversarially. A failed transaction request is a product integration failure, not evidence of an Ootle vulnerability.
